# Ранбук реализации админки VPN: сторонние подписки и маршруты

Цель: добавить в `stats.esmien.com` управление подписками провайдеров и тремя группами маршрутов: **Основной** (`general`), **Gemini** (`gemini`), **RU** (`ru`). Отдельный пул **LTE** управляет составом подписочной выдачи пользователям и не является сценарием маршрутизации Xray. Это инструкция для реализации, а не описание уже работающих функций. Шаги 1–7 выполнять на стенде. Эта инструкция сама по себе не разрешает менять боевой VPN.

## Состояние работ на 28.11.2026

Код: ветка `feat/vpn-admin`, рабочая копия `/root/vpn-service-admin`, фронт `web/admin_panel/`, бэк `router/admin/`. Стенд стоит по единственному адресу `https://test.ai.esmien.ru/vpn-admin/` с авторизацией существующей учётной записью панели и заменил предыдущую версию. Боевой VPN, его конфиги, выдача и службы не изменялись.

Сделано:

1. Шаг 1 выполнен: действующие исходники панели и аккаунтного API перенесены в ветку без изменения путей публикации. Интерфейс собран из утверждённого `vpn-admin-prototype.html`: используются его разметка и рендерер, отличаются только источник данных и подписи о тестовом режиме.
2. Срез бэка: FastAPI на Unix-сокете за nginx, `GET /api/subs` и `GET /api/routes`, оператор из `X-VPN-Operator`, SQLite в WAL с правами `0700`/`0600`. Ответы не содержат URL подписок, ссылок узлов и внешних IP подписочных узлов.
3. Реальные данные: `create_snapshot.py` делает закрытый разовый снимок `config.json`, `subs.json`, `policy.json`; `snapshot_import.py` переносит его в тестовую SQLite (2 подписки, 64 узла, 3 сценария). Служба не видит `/root/vpn-router`, `/root/.secrets` и Docker socket.
4. Пробы: `general` — HTTPS-запрос через отдельный временный Xray/Hysteria-клиент, Gemini и RU — существующий `route_probe.py`. Неподтверждённый результат выводится как `unknown`, задержка HTTPS не называется пингом.
5. Мок-слой взаимодействия: галочки четырёх пулов, имя узла, имя подписки, удаление с вводом `DELETE`, замена URL, мок-обновление, добавление подписки, основной выход и порядок резервов. Всё пишется только в отдельную SQLite `/var/lib/vpn-admin-preview-test/snapshot.sqlite3` и переживает перезапуск службы; к Xray и выдаче не применяется.
6. Проверки: `pytest` (7 тестов — контракты, границы доступа, моки, переоткрытие БД) и Chromium-smoke по всем действиям интерфейса. Отдельно подтверждено, что боевые файлы при пробах и моках остаются побайтно неизменными.

Осталось:

1. Шаги 2–4 в части записи: единый путь записи, журнал `apply_journal`, транзакция blue/green, публикация LTE, `reconcile_policy` на реальных данных. Сейчас это моки без применения.
2. Шаг 3 целиком: реальная загрузка подписки с SSRF-защитой, разбор форматов, `refresh_reviews`/`needs_review`, сопоставление узлов по отпечатку. Кнопки «Добавить», «Обновить» и «Заменить URL» данные провайдера не запрашивают.
3. Шаг 5: лимит и отмена заданий, калибровочный контроль через независимый выход, проверка каждой обязательной цели RU (текущая проба подтверждает только HTTP-ответ), сохранение результатов с версией подключения, цель `cp.cloudflare.com/generate_204` вместо текущей.
4. Шаг 6: сторож, `watchdog_state`, `runtime_generation`, индикация `health`. В боевой конфигурации используется `leastPing`, поэтому активный выход и порядок резервов в интерфейсе пока не определены.
5. Сроки подписок: ежедневное обновление `expires_at` и перевод `sub_expiry.py` на SQLite (Шаг 3, пункты 6–7).
6. Шаг 7: приёмочные тесты стенда (сбой после каждой стадии журнала, единый `flock`, сохранение inode, сквозной туннель). Шаг 8, боевая выкатка, без отдельного разрешения не начинается.

Ограничения стенда: тестовая БД содержит секреты и пока не имеет отдельной резервной копии; результаты проб живут в памяти и теряются при перезапуске; после замены URL проверки продолжают идти по исходному снимку; новая подписка создаётся без узлов.

## Шаг 1. Собрать стенд и показать макет

1. Работай в ветке `feat/vpn-admin` репозитория `vpn-service` (рабочая копия ветки на хосте — `/root/vpn-service-admin`). Фронт развивай поверх `web/admin_panel/index.html`, перенесённого из действующей панели без правок. Старый API находится в `router/admin/subgen_api.py`; новый FastAPI добавляй рядом, не заменяя аккаунтный обработчик. Сверь базу с `/root/vpn-router/` и не затирай незавершённые изменения в `provider_sources.py`. Подготовь отдельную рабочую директорию, тестовую SQLite, вымышленные подписки и изолированные конфиги обоих цветов Xray. Не подключай боевые таймеры и не запускай новый `provider_sources.refresh` на боевых данных. **Проверка:** в настройках стенда нет боевых путей записи; мок провайдера доступен стенду, а тесты не трогают файлы и сервисы хоста.
2. В качестве ориентира по интерфейсу используй утверждённый `vpn-admin-prototype.html` из `files/output`. Исходный макет не правь и не публикуй вместо работающего стенда. В карточке подписки показывай полный сохранённый список и четыре независимых фильтра: «Основной», «Gemini», «RU», «LTE». Поставлена галочка — узел допущен в пул; снята — исключён из него. Результат пробы помогает выбирать, но не ставит и не снимает галочки автоматически. На экране маршрутов оставь три сценария: свои выходы и только допущенные в нужный пул узлы. У каждого сценария покажи основной, текущий и очередь резервов. Рядом со своими выходами покажи подтверждённый внешний IP, у подписочных узлов IP не выводи. **Проверка:** переключение Gemini не меняет RU и LTE; LTE влияет только на выдачу; в резерв нельзя выбрать узел вне соответствующего пула.

## Шаг 2. Подготовить хранилище и импорт

1. Опиши действующие точки чтения и записи. Начни с `subgen_api.py` (включая `route_control.py`), `scenario_fallback.py`, `route_transaction.py`, `fetch_provider_subscriptions.py`, `sub_expiry.py`, `make_sub.py`, генератора конфигов и аккаунтных операций. Админка и сторож сейчас используют файловую политику; таймер срока читает `subs.json`, генератор LTE — `whitelist_links.json`. `vpn-entry-stack/references/admin-api.md` описывает целевую архитектуру аккаунтов и статистики; эту миграцию здесь **не** делать. **Проверка:** для каждого писателя указан файл, служба, переход на новый путь или причина оставить его в прежнем контуре.
2. Добавь SQLite только для сторонних подписок и управления маршрутами. Используй один путь записи: API и локальные команды таймеров вызывают одни и те же бизнес-операции и репозитории, не пишут таблицы или конфиги в обход этого слоя. Реализуй HTTP-контракты на FastAPI/Pydantic v2, SQLite — через SQLAlchemy 2.x, доступ к данным — репозитории и единица работы. Схема ниже задаёт данные и ограничения, а не продублированный JSON. Аккаунты, пользовательские URL/токены, `/u/`, статистику и состав профилей не переносить. **Проверка:** существующие аккаунтные операции работают без SQLite; отключение старых писателей подписок и маршрутов не отключает статистику или аккаунты.

| Таблица | Ключ и данные |
| --- | --- |
| `provider_sources` | `sub_id`; версия источника, имя, секретный URL, Telegram, срок `expires_at`, время его последней проверки `expiry_checked_at`, `fetch_status`, очищенная ошибка, время последней удачной публикации. |
| `provider_nodes`, `node_pools` | `node_id`; связь с источником, версия подключения, имена, секретная ссылка, транспортный отпечаток. Пул: уникальная пара `(node_id, pool)`; `pool` — `general`, `gemini`, `ru` или `lte`. Строка есть — узел допущен; строки нет — исключён. |
| `own_names`, `own_egress` | Неизменяемый тег своего выхода, имя и версия подключения. Результат измерения: тег, версия подключения, подтверждённый внешний IP либо `null`, время проверки. |
| `route_policies`, `route_fallbacks` | Один ряд на сценарий: `policy_version`, `runtime_generation`, `primary`, `active`, `active_role`, последнее состояние здоровья; резерв: `(scenario, position, exit_id)`, дубли `exit_id` в сценарии запрещены. Ссылки на узлы и свои теги проверяются сервисом до применения. |
| `refresh_reviews`, `refresh_candidates` | Один ожидающий разбор на подписку; `review_id`, версия источника, закрытый снимок полного ответа, `candidate_id` и допустимые старые ID. |
| `probe_jobs`, `probe_results` | `job_id`, владелец задания, сценарий, выбранная область, снимок целей, состояния и время; у результатов — `exit_id`, сценарий, версия подключения и номер запуска. |
| `watchdog_state` | `(scenario, runtime_generation, exit_id, connection_version)`; серии успехов и отказов и номер последнего учтённого тика. |
| `issued_node_links` | `issued_node_id`, ссылка на провайдерский `node_id` или собственный `exit_id` (при отвязке `NULL`), вид выдачи, внутренний адрес существующего элемента, закрытый отпечаток его подключения, исходное и последнее опубликованное имя. 3. Включи `journal_mode=WAL` при создании БД, а `foreign_keys=ON` и `busy_timeout=5000` — для каждого соединения. Каталог `0700`; БД `0600`; WAL/SHM и копии недоступны посторонним. Не храни БД или ключи в git. Не выполняй HTTP, пробы и ожидание дочернего процесса внутри транзакции записи. Если писатель не освободился за отсрочку, возвращай `503` с кодом `storage_busy`. **Проверка:** на двух соединениях ошибочная ссылка отклоняется, занятый писатель не приводит к потере данных; из резервной копии SQLite восстанавливается вместе с данными, ещё находившимися в WAL.
4. Импортируй на копии источники, узлы, пулы, имена, выбранные и действующие выходы. При переходе в LTE-пул включи только однозначно сопоставленные уже выданные узлы; отдельные элементы старой выдачи, не управляемые подпиской, сохраняй отдельно и не меняй галочками. При неоднозначном сопоставлении или невозможности воспроизвести выдачу не переключай её до разбора. Сохрани порядок резервов и прочие правила Xray. Если действующая конфигурация не представима без изменения правил или состава выходов, останови переход и выпиши расхождения. Сохрани однозначные старые ID либо перенеси все их ссылки вместе. После переключения SQLite — единственный владелец импортированных данных. `subs.json` используется для импорта и восстановления старой версии, но не обновляется и не читается новыми службами. **Проверка:** сравнение до/после не раскрывает ключи и не меняет текущие подключения, выдачу, правила и их порядок. Ни один старый процесс не пишет импортированные настройки параллельно с новой службой.

5. Подними отдельный `vpn-admin.service` с одним процессом FastAPI. Слушай только Unix-сокет `/run/vpn-admin/api.sock`, доступный службе и системному nginx, не открывай TCP-порт. В `stats.esmien.com` направь точные пути `/api/subs` и `/api/routes` и их дочерние пути `/api/subs/…` и `/api/routes/…` на этот сокет с сохранением `/api`. Остальной `/api/` продолжает идти на старый `subgen_api.py` с существующим удалением префикса; `/data.json`, `/u/` и аккаунтные операции не переносить. После перехода отключи в старом обработчике запись и пробы старым маршрутом, включая прямые обращения к старому слушателю. Сторож запускай прежним таймером как локальную команду нового слоя маршрутов, а не как ещё один HTTP-сервис. **Проверка:** запросы подписок/маршрутов приходят в FastAPI, аккаунтные — в старый процесс; старый обработчик больше не применяет маршруты даже напрямую, локально.
6. Сохрани действующие сетевые ограничения и Basic Auth панели в новых nginx location. На сокет передавай проверенное имя через `X-VPN-Operator`, перезаписывая одноимённый заголовок клиента; пароль дальше не передавай. FastAPI разрешает доступ только имени владельца из локальной конфигурации; не доверяй имени вне закрытого сокета. Для записей проверяй точный `Origin` панели и JSON. **Проверка:** посторонний Basic Auth либо поддельный заголовок не дают прав оператора, запрос с другого origin не меняет состояние, прямой TCP-доступ к FastAPI отсутствует.

## Шаг 3. Реализовать загрузку и разбор совпадений

1. Сделай `provider_sources.py` загрузчиком без побочных записей. На разрешённых данных подтверди используемые форматы Happ и заголовки (`x-device-os` и `x-ver-os` не считать подтверждёнными). Поддержи проверенный запасной клиентский профиль v2rayTun. Для SSRF-защиты проверяй каждый переход, адреса IPv4/IPv6 и фактическое соединение; используй проверенный публичный IP на уровне транспорта, не подменяй URL. Сохраняй исходные `Host`, TLS `server_hostname`/SNI и проверку сертификата. Отключи неявные прокси, ограничь переходы, время и размер. Не пересылай `x-hwid` и чувствительные заголовки на другой origin. **Проверка:** на подставном транспорте непубличный или неподтверждённый адрес отклоняется, а разрешённый HTTPS проходит с исходным TLS-именем.
2. Разбери полный ответ. Читай срок из `subscription-userinfo`; при `expire=0` или отсутствии срока отдавай `null`. Фильтруй информационные фальш-ноды отдельно от рабочих узлов. HTTP-ошибка, истёкшая подписка, пустой/битый ответ или одни заглушки → `error`. При ошибке сохраняй последнюю рабочую копию, пулы, маршруты и LTE. Не затирай известный прежний срок пустым значением при сетевой ошибке. Для спойлера собери очищенный текст с переносами строк, а короткую версию обрежь после 28 символов с многоточием. **Проверка:** ответ с одной заглушкой и рабочими узлами не разрушает список; при `502` меняется диагностика, не трафик.
3. Сопоставь успешный полный ответ с прежними узлами той же подписки. Создавай случайный `node_id` один раз; отпечаток определяет совпадение, а не ID. Сравни протокол, адрес, порт, транспорт, SNI/Host, путь/службу и параметры защиты; имя и `host:port` по отдельности непригодны. Автоматически сохраняй ID и ручные настройки только при взаимно однозначном совпадении. Если выбор неоднозначен, отложи весь снимок в `refresh_reviews` и выставь `needs_review`: ничего из этого ответа пока не применять. **Проверка:** переименование сохраняет ID и назначения, разные транспорты на одном порту не сливаются, совпадение между подписками не переносит права или настройки.
4. Перед записью заново прочитай источник и проверь его версию. Увеличивай версию при изменении источника и фиксации нового результата; новая загрузка делает старый разбор недействительным. Данные узлов с ручными настройками перечитывай при записи. Храни версию подключения отдельно, повышай при изменении подключения, но не при переименовании. При успешном применении снимка обнови `last_success_at`; если исчезли узлы, применяй согласование из Шага 4 в той же операции. **Проверка:** опоздавший результат не возвращает удалённую подписку, не затирает URL, имена или галочки и не отменяет более свежий результат.
5. Подключи контракты ниже. Проверь маршрутизацию nginx из Шага 2. Новую схему и новый UI выкатывай вместе, а не по одному. Для `needs_review` отобрази «Нужно сопоставление», безопасные варианты и кнопку подтверждения. В каждой строке разреши выбрать допустимый прежний узел либо «Новый узел»; при выборе нового он не наследует пулы. Предупреди, что подтверждение полного снимка может убрать пропавшие назначения. При конфликте обнови карточку, не пересылай старое решение. **Проверка:** пользователь может разрешить конфликт без сырых ссылок; дубликат старого ID или неполный набор решений не применяется.

`GET /api/subs` → `200`. Все даты UTC ISO 8601 либо `null`; `review` равен `null` вне `needs_review`. Пример:

```json
{"subscriptions":[{"sub_id":"sub_demo","version":8,"name":"Пример","tg_url":"https://t.me/example","fetch_status":"needs_review","expires_at":null,"expiry_checked_at":null,"last_success_at":"2026-11-20T10:00:00Z","error_snippet":null,"error_full":null,"nodes":[{"node_id":"n_a","original_name":"NL","custom_name":null,"pools":{"general":true,"gemini":false,"ru":false,"lte":false},"probes":{}}],"review":{"review_id":"rev_demo","source_version":8,"candidates":[{"candidate_id":"c1","label":"Новый NL","options":[{"node_id":"n_a","label":"Старый NL"},{"node_id":"n_b","label":"Резерв NL"}]}]}}]}
```

| Ручка | Тело запроса | Успешный ответ |
| --- | --- | --- |
| `POST /api/subs/add` | `name`, `url`, `tg_url` | `201`: `subscription`, `switched_routes`, `delivery_update`. |
| `POST /api/subs/update` | `sub_id`, `version`, необязательные `name`, `url`, `tg_url` | `200`: тот же формат. `error`/`needs_review` в карточке не означают, что новый список принят. |
| `POST /api/subs/review/resolve` | `sub_id`, `review_id`, `source_version`, `decisions` | `200`: тот же формат. Применить целиком, если все решения допустимы и прежние ID использованы не более одного раза. |

```json
{"sub_id":"sub_demo","review_id":"rev_demo","source_version":8,"decisions":[{"candidate_id":"c1","node_id":"n_a"}]}
```

В решениях `node_id: null` означает «Новый узел». Неполный или невалидный набор — `400`, устаревший разбор или версия — `409`; ничего частично не применять. `subscription` в ответе имеет форму элемента списка; строки `switched_routes` описаны в Шаге 4.

Размести форму «Добавить» с полями «Название», «URL подписки», «Telegram» и не спрашивай срок. В карточке покажи имя, Telegram, срок, время проверки срока (`expiry_checked_at`), «Активна»/«Не работает» именно для загрузки и время последнего успеха. Срок выводи как «ДД.ММ.ГГГГ — осталось N дней»: больше 7 — зелёный, 7–4 — оранжевый, 3–0 или истёкшая — красный; при `null` — «нет информации от провайдера». Поле старого URL оставляй пустым; нормализуй Telegram только в `https://t.me/<path>`. Никогда не отдавай старый URL или сырые `vless://`, `trojan://`, `hy2://`, `hysteria2://` в браузер, аудит или логи. Показывай строки через `textContent`, не `innerHTML`.

6. Сохрани ежедневную проверку сроков без второго источника данных. В `vpn-sub-expiry.service` перед уведомлениями вызывай локальную команду новой админки: она обновляет только `expires_at` и `expiry_checked_at` через тот же защищённый HTTP-загрузчик, с ограниченным временем на подписку и на весь запуск. Настрой вызов обновления как `ExecStartPre` с игнорированием ненулевого кода именно этой команды: сбой опиши в журнале, а чтение последнего срока и уведомления всё равно выполни. Ошибку самого чтения БД не игнорируй. Не импортируй узлы и не меняй маршруты, `fetch_status` или состояние разбора. Применяй только подтверждённый срок из валидного ответа; нормальный полный ответ без срока или с `expire=0` даёт `null`. Сетевая ошибка сохраняет прежний срок и время; подтверждённый истёкший срок из заголовка не отбрасывай. Перед записью сверяй источник и URL (или версию источника) и время наблюдения срока, чтобы опоздавшая проверка не затирала результат ручного обновления. Сетевой запрос — вне лока; запись через общий путь и только после восстановления незавершённых операций. **Проверка:** продление отражается без ручного обновления; истечение, таймаут и конкурирующее обновление не меняют список узлов и маршруты.
7. Переведи `sub_expiry.py` на `sqlite3` с `mode=ro`, без сетевых запросов к провайдеру и без fallback на JSON. Читай из `provider_sources` только ID, имя, срок и время его проверки. Если этап обновления не получил свежую дату, используй последнюю сохранённую с пометкой «по последней проверке»; если БД не читается, заверши с ошибкой, не меняя состояние уведомлений. Сохрани расписание, Telegram и уведомления за 3/2/1 день; после истечения уведомляй один раз на дату окончания, дедуплицируй по `sub_id` и сроку. При миграции перенеси старую отметку только при однозначном сопоставлении имени. Пиши отметку после успешной отправки; имена экранируй для Telegram. **Проверка:** служба обрабатывает известный, неизвестный и просроченный сроки, переименование не дублирует уведомление, повторный тик после истечения не шлёт его снова. Отдельную JSON-проекцию для таймера не создавать; откат маршрута не публикует неподтверждённую дату.

## Шаг 4. Реализовать единое применение маршрутов и имён

1. Реализуй `reconcile_policy` для удаления подписки, подтверждённого исчезновения узла из полного ответа и снятия галочки пула. Удали недоступные ID из резервов, сохрани порядок остальных. Если больше не допущен `primary`, назначь основным свой выход сценария: по умолчанию `direct` / `nl` / `ru1` (проверь теги на стенде). Если пропал `active`, переключи на свой выход; при сохранённом другом `primary` пометь свой выход как `temporary_own`. Если исчез только `primary`, а `active` остаётся допущенным и входит в новую очередь, не срывай рабочее подключение: сторож проверит новый `primary`. Не повышай первый резерв до основного. Не вызывай согласование из-за ошибки загрузки. Для LTE не меняй ни основной выход, ни очередь: его галочка меняет только состав выдачи. **Проверка:** удаление рабочего активного узла переводит на свой выход, а ошибка загрузки оставляет активный маршрут без изменений.
2. Сформируй конфигурацию из новой политики. У каждого сценария один `outboundTag` текущего выхода; не заменяй целые группы отдельных правил одним доменом. Сохрани порядок `api-in`, правил входов, приватных сетей, своих доменов и существующих исключений. Финальное правило для трафика без совпадений ведёт на `active` Основного. Дедуплицируй выходы по тегу, проверяй ссылки отдельным lint: одного `xray -test` недостаточно. Hysteria2 подключай через SOCKS5 `hy2_bridge.py`, не передавай Hysteria2 напрямую в Xray. **Проверка:** один узел в двух группах имеет один тег; служебные маршруты и исключения совпадают с исходными.
3. Сделай одну точку применения с `/var/lock/vpn-config.lock`. Под локом перечитай версии, запиши план операции и вызывай внутреннюю функцию применения. Публичные `set_policy` и `recover` уже захватывают лок: раздели обёртку и внутреннюю функцию. Ни внутренние функции, ни дочерние команды не должны повторно брать этот же `flock`. Под тем же локом сериализуй старых писателей общего конфига и выдачи, не переводя их аккаунтные данные в SQLite. **Проверка:** одновременные правки из админки и сторожа либо последовательно применяются, либо устаревшая отклоняется; восстановление не зависает.
4. Запиши журнал и закрытые снимки до изменения артефактов. Для двух файлов, смонтированных по одному (`config.json`, `config.b.json`), записывай и восстанавливай содержимое поверх: `r+b`, `seek`, `write`, `truncate`, `fsync`. Для остальных файлов используй временный файл в том же каталоге с нужными правами (`0600` для секретных), `fsync`, `os.replace`, `fsync` каталога. Подготовь мосты, проверь неактивный цвет, переключи новые подключения и проверь через вход. До успешной проверки публикуй в API прежнее применённое состояние. Только затем короткой транзакцией зафиксируй новую ревизию и итог журнала. Запись SQLite не должна оставаться открытой во время blue/green. Xray не перезапускается для операции, которая меняет только выдачу или счётчики. **Проверка:** inode обоих файлов не изменились, контейнеры видят нужные данные, отказ неактивного цвета не переключает трафик.
5. Восстанавливай незавершённую операцию под тем же локом до новых записей. Сверь журнал, БД, конфиги, содержимое выдачи и реальный цвет; закончи подтверждённую операцию или верни прежнее состояние. На ошибке не возвращай успех клиенту API. После успеха или отката останови только ненужные постоянные мосты: учти действующие подключения в старом цвете, откат и выполняемые пробы. Временные мосты убирают сами пробы. **Проверка:** прерывание на каждой стадии оставляет воспроизводимое состояние; повторное восстановление безопасно; откат не теряет используемый мост.
6. Публикуй LTE из узлов с установленной галочкой `lte` и неуправляемых элементов старой выдачи, сохранённых при импорте. Снятие галочки, подтверждённое исчезновение узла или удаление подписки удаляют соответствующую управляемую ноду из выдачи. Новые узлы по умолчанию выключены. При `error` или ожидающем разборе сохраняй прежний состав. Используй `<sub_name>/<custom_name>` с исходным именем при отсутствии `custom_name`; при коллизии добавляй стабильный суффикс. Обновляй три формата (`list.txt`, `clash.yaml`, `singbox.json`) и `issued_node_links` одним применением с журналом и откатом. Сохраняй порядок оставшихся элементов; новые добавляй в стабильном порядке. Не меняй ключи, токены и адреса существующих элементов; включение допускает только сохранённые узлы, поддерживаемые генератором. Если операция оставляет выпуск без узлов или один из форматов не собирается, отклони операцию целиком, верни прежние настройки и файлы. Состав основной подписки не меняй. **Проверка:** включение и выключение отражаются во всех трёх форматах, переименование меняет только подпись, ошибки загрузки сохраняют выпуск, откат восстанавливает ссылки и состав.
7. Подключи кнопки удаления, редактирования и применения. Показывай уведомление после успешного переключения или смены основного выхода; при сбое — ошибку. После переименования показывай, где применилось имя. **Проверка:** нельзя удалить без `DELETE`, а изменение имени без привязки не изображает обновление выдачи.

| Ручка | Запрос | Успешный ответ |
| --- | --- | --- |
| `POST /api/subs/delete` | `sub_id`, `version`, `confirm: "DELETE"` | `200`: `ok`, `switched_routes`, `delivery_update`. |
| `POST /api/subs/node` | `sub_id`, `node_id`, необязательные `custom_name` и частичный `pools` | `200`: `ok`, `switched_routes`, `delivery_update`. |
| `GET /api/routes` | Без тела | `200`: `own_names`, `own_egress`, `scenarios` (все три). |
| `POST /api/routes/apply` | `scenario`, `policy_version`, `primary`, упорядоченные `fallbacks` | `200`: такой же снимок, как GET, только после применения. |

Ровно `DELETE` проверяет сервер, иначе `400`. Для `sub_id: "own"` меняй только имя своего тега; `custom_name: null` сбрасывает имя, отсутствие поля не трогает его. `pools` меняет только переданные ключи `general`, `gemini`, `ru`, `lte`. `lte` не принимается как `scenario`. Запросы добавления, обновления и ручного разбора также возвращают `delivery_update`; при неизменной выдаче используй `not_requested` или `admin_only` по правилам ниже. Примеры:

```json
{"sub_id":"sub_demo","version":8,"confirm":"DELETE"}
```

```json
{"sub_id":"sub_demo","node_id":"n_a","custom_name":"NL офис","pools":{"general":true}}
```

```json
{"ok":true,"switched_routes":[],"delivery_update":{"state":"published","kinds":["lte"]}}
```

`delivery_update.state`: `published` — изменился фактически опубликованный состав или имена, `admin_only` — имя или допуск сохранены, фактический выпуск не изменился, `not_requested` — операция не требовала пересборки выдачи. Для последних двух `kinds: []`. При сбое переиздания откати изменение и верни ошибку. Заполняй `switched_routes` только там, где изменился `active` или `primary`. Формат элемента:

```json
{"scenario":"general","old_active":"n_a","active":"direct","old_primary":"n_a","primary":"direct"}
```

Пример `GET /api/routes` для одного сценария (реальный ответ содержит три):

```json
{"own_names":{"direct":"Наш выход"},"own_egress":{"direct":{"ip":null,"checked_at":null}},"scenarios":{"general":{"policy_version":12,"own_exit_ids":["direct"],"primary":"direct","fallbacks":["n_a"],"active":"direct","active_role":"primary","health":{"state":"degraded","reason":"fallbacks_exhausted","checked_at":"2026-11-23T21:00:00Z"}}}}
```

```json
{"scenario":"general","policy_version":12,"primary":"direct","fallbacks":["n_a"]}
```

Версия относится к одному сценарию. Меняй `policy_version` при изменении сохранённого `primary` или `fallbacks`, в том числе при удалении из пула. Смена `active`, имени или состояния здоровья не меняет `policy_version`. При ручном изменении `primary` применяй новый выбранный основной, а при изменении только резервов сохраняй `active`, если он в обновлённой очереди или уже исполняет роль `temporary_own`. Если временный выход не совпал с основным, сохраняй его временную роль, даже когда его тег есть среди резервов. Если из очереди убран текущий обычный резерв, активируй сохранённый `primary`. Пересчитай роль по итоговому выбору; явное назначение текущего выхода основным снимает роль временного. Повтор того же выбора — без перезапуска. `active` и `health` назначает сервис, не браузер. Проверяй существование, допуск, дубли и отсутствие `primary` в `fallbacks`. Для устаревшей версии верни `409`:

```json
{"error":{"code":"stale_policy"},"scenario":"general","policy_version":13}
```

Список подписок и пулы UI берёт из `GET /api/subs`. Для своих узлов `own_names` перечисляет доступные собственные теги с отображаемыми именами, включая значения по умолчанию; по `scenarios[scenario].own_exit_ids` UI показывает свои выходы, допустимые для сценария; сервер всё равно проверяет допуск. В `own_egress[tag]` отдай `{ip, checked_at}`: внешний IP, полученный через тот же выход и версию подключения, либо `null`, если не подтверждён. При смене подключения считай прошлое измерение устаревшим. У подписочных узлов не отдавай IP в публичном API. В спойлере «Наши серверы» покажи адрес рядом с именем или подпись «IP не подтверждён». Там же поставь рядом с отображаемым именем кнопку «Редактировать имя». Она отправляет `POST /api/subs/node` с `sub_id: "own"`, `node_id` равным исходному тегу и `custom_name`; сброс отправляет `null`. После ответа перечитай `own_names` и обнови подпись этого тега во всех группах. Теги `direct`, `nl`, `ru1` не редактируются, очередь не меняется, Xray не перезапускается. Если для своего выхода есть подтверждённая привязка к существующей выдаче, переиздаётся только имя; состав неизменен. На главном экране каждая подписка под своим спойлером, даже если отобранных узлов нет; неотобранные узлы не предлагай в выбор. Управление — «Основной», «В резерв», стрелки порядка и «Применить маршрут». Для узла в карточке показывай `<sub_name>/<custom_name>`, пока второе имя не задано — исходное имя узла; редактируется только правая часть. Для всех ручек этого ранбука проверяй права оператора, а для записи — JSON, допустимый `Origin` и защиту от подмены запроса. Общий формат ошибки — `{"error":{"code":"..."}}`, при необходимости с безопасными полями. У FastAPI переопредели ответ на неверный ввод: `400` с кодом, без исходного тела, отклонённого значения URL или сырого исключения; отсутствующая запись — `404`, ошибка применения — `503` с `apply_failed`.

## Шаг 5. Подключить пробы и остановку задания

1. Реализуй одну процедуру пробы выхода, которую используют и админка, и сторож. `general` проверяй коротким HTTPS-запросом к `https://cp.cloudflare.com/generate_204` через выход с ожидаемым `204`; измерь задержку, а для своего выхода запиши подтверждённый внешний IP и время измерения через этот же выход; сведения о подписочных IP не включай в ответы API. Для Gemini требуй ответ и признаки допустимого региона по текущим правилам; известный неподходящий регион — `bad`, нераспознанный — `unknown`. Для RU используй действующие цели сценария и проверяй каждую обязательную цель. Ответ WAF может подтвердить достижимость, но не работу функции. **Проверка:** успешный ответ не от нужного сервиса не засчитывается как работа Gemini/RU; тест не сводится к разрешению DNS или пингу адреса узла.
2. Различай `ok`, `bad`, `unknown`. Проверяй каждую обязательную цель; подтверждённая непригодность по правилам цели означает `bad`, а без такого отказа наличие хотя бы одной неопределённой обязательной цели означает `unknown`. Явный отказ соединения с узлом или его авторизации при исправном локальном клиенте — `bad`. При таймауте или сбое цели проверь независимую цель через тот же выход. Для Основного успех второй контрольной HTTPS-цели `https://connectivitycheck.gstatic.com/generate_204` с ожидаемым `204` достаточен. Для Gemini/RU бери контроль на том же тике из применённой очереди этого сценария: `primary`, затем `fallbacks` по порядку, пропуская проверяемый выход и подключения с тем же транспортным отпечатком, в том числе из другой подписки. Проверить контрольные кандидаты с ограниченным параллелизмом и таймаутом на каждый запрос; использовать первый успешный контроль по порядку. Для ручной калибровки, когда в очереди нет положительного контроля, дополнительно проверяй собственный выход сценария, если он независим. Произвольный прямой запрос с хоста не является контролем Gemini/RU. Выход подтверждает контроль только текущим успешным ответом на ту же обязательную цель по тем же правилам; недавний успех или `200` произвольного ресурса не подходит. Если проверяемый выход на цели ждёт до таймаута, а хотя бы один контроль проходит, результат проверяемого — `bad`, даже если общий HTTPS через него работает. Если не проходит ни один независимый контроль и явного отказа нет — `unknown`. Результат по каждой цели классифицируй после сбора первичных наблюдений всех нужных кандидатов, а не по уже вычисленным статусам других проб. Собирай первичные ответы один раз за тик и переиспользуй их для контроля и выбора резерва, без рекурсивных проб; не обрезай список постоянным префиксом, который исключит поздний рабочий резерв. Если контроль недоступен и итог текущей пробы — `unknown`, не переключай трафик по этому результату; отметь, что проверка недоступна. Независимо подтверждённые отказы транспорта обрабатывай по Шагу 6. Локально не запустившийся тестовый процесс — `unknown`. **Проверка:** падение контрольного сайта, ошибка локального процесса и реальный отказ выхода дают разные результаты.
3. Реализуй фоновые задания с общим лимитом восемь ручных проб, таймаутом и отменой. Назначай временным прокси отдельные loopback-порты без гонки; временный Hysteria2 запускай через `hy2_bridge.py` с уникальной меткой и каталогом. В `finally` останови именно свой мост и удали временные процессы и файлы, в том числе после частичного старта. Для перезапуска сервиса предусмотри очистку его собственных осиротевших временных процессов, не трогая постоянные мосты. Пробы не держат лок применения или транзакцию записи. **Проверка:** при отмене и таймауте временных процессов, файлов и занятых портов не остаётся; чужое задание продолжает работать.
4. Сохраняй результаты точечно с версией подключения и номером запуска. Для устаревшей цели или результата более старого запуска ничего не публикуй. После запроса отмены не публикуй новые результаты; уже сохранённые не стирай. После рестарта незавершённые задания получат `failed`/`interrupted`. Ни одна ручная проба не меняет маршрут. **Проверка:** переименование или правка пула не затирается, старая проба не перезаписывает новую.

| Ручка | Действие |
| --- | --- |
| `POST /api/routes/probe` | `202` со снимком задания. Одинаковый активный запуск того же оператора возвращает тот же `job_id`; пустая выборка — `400`/`empty_probe_scope`. |
| `GET /api/routes/probe/{job_id}` | `200` со снимком задания; чужое или неизвестное — `404`. |
| `POST /api/routes/probe/{job_id}/cancel` | Тело `{}`; `202` с `cancelling` либо `200`, если уже завершено. Чужое или неизвестное — `404`. |

```json
{"scenario":"gemini","scope":"calibration","sub_id":"sub_demo"}
```

`calibration` — весь сохранённый список подписки, `pool_subscription` — выбранный пул подписки; в обоих случаях нужен `sub_id`. В остальных задачах `sub_id` в ответе равен `null`. `pool_all` — весь отобранный пул со своими, `pool_own` — только свои, для них `sub_id` запрещён. Ошибка загрузки не исключает сохранённые узлы.

```json
{"job_id":"job_demo","scenario":"gemini","scope":"calibration","sub_id":"sub_demo","state":"running","total":4,"completed":1,"error":null,"results":[{"exit_id":"n_a","status":"ok","latency_ms":180,"checked_at":"2026-11-23T21:00:00Z"}]}
```

`state`: `queued`, `running`, `cancelling`, `cancelled`, `succeeded`, `failed`. `cancelled` — после уборки. `succeeded` — задание закончено, не все узлы обязательно исправны. `completed` включает обработанные цели, чьи устаревшие результаты отброшены. Для `failed` — безопасный объект `error` с кодом. Завершённые задания доступны 24 часа. Такой же объект измерения без IP использует `nodes[].probes[scenario]`. LTE — фильтр выдачи, не отдельный сценарий проб: решение о допуске принимают по результатам проверок узла в карточке.

5. В браузере опрашивай только свой `job_id` и меняй кнопку этой группы на «Остановить». Обозначай ожидание, проверку, остановку, завершение или ошибку без прогресс-бара; `unknown` рисуй отдельно от подтверждённого отказа. **Проверка:** две группы можно проверить одновременно; остановка одной не меняет результаты второй.

## Шаг 6. Подключить сторож и индикацию маршрута

1. На каждом тике `vpn-scenarios.timer` сними `runtime_generation`, текущий `active`, `primary`, очередь и версии подключений. Проверяй текущий выход, а если он не `primary` — ещё и `primary`. Пробы делай вне лока. Сохраняй серии в `watchdog_state`; один результат учитывай один раз. `unknown` прерывает серию, но не считается ни подтверждённым отказом, ни успехом. Не включай старый `vpn-failover.timer`. **Проверка:** два разных запуска таймера дают два результата одной серии; смена подключения или маршрута не наследует старые результаты.
2. Выполняй решения в этом порядке. **Проверка:** таблица ниже покрыта параметризованным тестом, который сверяет выбранный выход и число вызовов применения.

| Условие | Действие |
| --- | --- |
| Работает `primary`; он уже активен | Оставить маршрут. Два `ok` подряд снимают деградацию без перезапуска. |
| Активен не `primary`; `primary` дал два `ok` подряд | Вернуть трафик на `primary` сразу, даже если резерв исправен. |
| Активный выход дал меньше двух `bad` подряд | Оставить маршрут. Разовая ошибка не переключает. |
| Активный выход дал два `bad` подряд; `primary` не восстановился | Если упал `primary` — начать с первого резерва. Если обычный резерв — со следующего номера. Если `temporary_own` — с первого, пропустив отказавший текущий тег, даже если он числится в очереди. Взять первый выход, подтвердивший работу; задержка не меняет порядок. |
| Перебор не подтвердил ни одного рабочего варианта | Вернуть `active` на `primary`. Если он уже активен, не перезапускать. Статус `degraded`: `fallbacks_unconfirmed`, если остались неопределённые пробы, иначе `fallbacks_exhausted`. |

3. Перед учётом результатов, сохранением счётчиков и применением перечитай состояние под локом Шага 4. Если изменились `runtime_generation`, роли, очередь или версии проверенных подключений, отбрось устаревшее решение. Повышай `runtime_generation` при изменении активного выхода, очереди или параметров его проверяемых подключений. При изменении `active_role` без смены тега тоже увеличивай `runtime_generation`. Если изменение не касается подключений `primary`, но сменился активный выход, не переноси серию успехов `primary` в новое поколение. При ручной смене выхода сбрасывай здоровье в `unknown`; при защитном переходе выставляй `temporary_own`/`active_removed`. При подтверждённом уходе на резерв выставляй `fallback`/`primary_failed`, при подтверждённом возврате — `primary_ok`. Храни здоровье рядом с применённым состоянием; если выход не меняется, обновляй только здоровье и счётчики. **Проверка:** выбор владельца, сделанный посреди пробы, не отменяется сторожем; при лежащих резервах нет холостого переключения цветов.
4. Выведи `health` из `GET /api/routes`. Роль `active_role`: `primary`, `fallback`, `temporary_own`. `health.state`: `unknown` до пробы или пока нет определённого результата, `primary_ok` при подтверждении основного, `fallback` для рабочего резерва, `temporary_own` после защитного перехода на свой выход, `degraded` после неудачного перебора. `reason` — `null` или код `primary_failed`, `active_removed`, `probe_unconfirmed`, `fallbacks_exhausted`, `fallbacks_unconfirmed`; `checked_at` — время последнего относящегося к состоянию результата либо `null`. Если проба текущего выхода неопределённа и маршрут не сменился, при отсутствии уже зафиксированной деградации выставь `unknown` с причиной `probe_unconfirmed`; уже зафиксированную деградацию не стирай. В UI подпиши `probe_unconfirmed` «Проверка маршрута недоступна»; это не означает отказ выхода. В UI покажи «Резервы исчерпаны» или «Нет подтверждённого рабочего резерва» по коду причины; временный свой выход подпиши отдельно. **Проверка:** UI отличает исправный резерв от отсутствия рабочего резерва и не путает ручную пробу с состоянием сторожа.

## Шаг 7. Принять работу на стенде

1. Запусти `python -m pytest -q` из корня рабочей копии VPN с путями стенда. Принимай не общий зелёный статус, а все сценарии: загрузка с ошибкой и без неё, разбор совпадений и `409`, параллельный API и SQLite, сбои после каждой стадии журнала, отмена, привязка имён выдачи, один `flock`, сохранение inode обоих конфигов и уборка мостов. **Проверка:** каждый из этих сценариев имеет тест; заготовка загрузчика без тестов Шага 3 не считается готовой.
2. Открой панель через стендовый прокси. Пройди цепочку: добавить подписку → отобрать узел → применить очередь → вызвать отказ → дождаться резерва → восстановить основной. Отдельно проверь отмену, таймаут `primary` при работающем HTTPS и успешной проверке через поздний резерв Gemini/RU (два отказа → переключение), отсутствие положительного контроля (покажи `unknown`, не переключай), исчерпание очереди и временный свой выход. Поменяй подпись `direct` и сбрось её: маршрут и тег неизменны. Сверь внешний IP у своего выхода с ответом сетевой пробы; у подписочных узлов поля IP нет. Включи и выключи LTE-узел: состав трёх форматов изменился, основной профиль и три очереди не затронуты. **Проверка:** на экране виден ожидаемый выход и его состояние; после подтверждения восстановления резерв больше не активен.
3. Проверь подключение через тестовый клиентский туннель. Сверь выходной IP и назначение трафика для каждой группы, при неудачной проверке нового цвета подтверди откат и сохранение выдачи. Отдельно проверь старую статистику, аккаунтные операции и `/u/`; сравни маршрутизацию прокси и права владельца. Прогони суточную проверку срока на стенде с фиктивным провайдером и Telegram, включая сбой обновления и откат после неприменённой операции. **Проверка:** сквозное подключение и откат подтверждены результатами, а не только `xray -test` или скриншотом.

## Шаг 8. Перейти на боевой контур только после разрешений

Попроси владельца проверить свой туннель, профиль и применимость изменений на его устройстве. **Проверка:** владелец подтвердил работу из своей сети, остальные клиенты не переключались на новый вариант.
